## 0. 세션 시작 규칙 — Drill-Me 우선

**배경**: 화면기획서(와이어프레임/화면정의서) 없이 대략적인 합의만 가지고 바이브코딩을 진행한다. 이 상태에서 곧바로 코드부터 짜면, 사람마다 다르게 이해한 채로 화면이 나온 뒤에야 어긋난 걸 발견하게 된다. 그래서 새로운 화면/기능을 다루는 세션은 코드를 짜기 전에 반드시 질문 단계(drill-me)를 먼저 거친다.

**트리거 조건** (다음 중 하나라도 해당하면 drill-me부터 시작한다):
- 새 화면, 새 컴포넌트, 새 사용자 플로우를 다루는 요청
- 해당 화면/기능에 대한 텍스트 기반 화면 스펙(진입점·컴포넌트·로딩/빈/오류 상태·인터랙션→API·T-ID)이 아직 프로젝트 파일에 없음
- 기존 화면 스펙이 있어도 이번 요청이 그 범위를 벗어남(예: 새로운 상태, 새로운 인터랙션 추가)

**생략 가능한 경우**:
- 이미 텍스트 기반 화면 스펙 문서가 존재하고, 이번 요청이 그 스펙 안에서만 구현하는 경우
- 순수 버그 수정, 내부 리팩토링 등 화면/플로우 변경이 없는 작업

**Drill-me 단계에서 반드시 확인할 질문 세트**:
1. 이 화면/기능의 진입점은 어디인가? (어느 탭·어느 화면에서 들어오는가)
2. 화면을 구성하는 컴포넌트는 무엇이고, 각각 필수인가 선택인가?
3. 로딩 중/데이터 없음(빈 상태)/에러 상태는 각각 어떻게 보여지는가?
4. 사용자의 각 인터랙션(클릭, 입력 등)은 어떤 API 엔드포인트와 연결되는가?
5. 이 기능은 어떤 T-ID에 해당하는가? (`docs/plan/PRD_ReMedi_v1.1.md`/`docs/plan/TRD_ReMedi_v1.1.md`/`docs/decision_log/`와 대조)
6. (해당 시) 이 화면이 다루는 데이터는 `profile_id` 기준인가, 다른 기준인가?

**진행 방식**:
- 위 질문의 답이 요청 메시지나 프로젝트 파일에 이미 다 있으면, 그 답을 요약해서 "이렇게 이해했다"고 확인받고 넘어간다.
- 답이 없는 항목이 있으면, 코드를 먼저 쓰지 않고 그 항목만 콕 집어서 되묻는다. 한 번에 다 물어볼 필요는 없지만, 답 없이 넘어가지 않는다.
- 확인이 끝나면 합의된 내용을 짧은 텍스트 스펙으로 정리해서 먼저 제시하고, 동의를 받은 뒤에 코드를 작성한다.

**판단 기준**: "이 요구사항만 보고 두 사람이 각자 다른 화면을 만들 수 있는가?" 답이 "그렇다"이면 drill-me가 아직 끝난 게 아니다.

**수동 강제 트리거 — STOP**

자동 트리거 조건에 안 걸리더라도, 팀원이 메시지 어디에든 `STOP`이라고 쓰면 다음을 무조건 한다:
1. 코드 작성 중이었다면 즉시 멈춘다(이미 작성한 코드를 계속 이어쓰지 않는다).
2. 지금까지 요청 내용을 바탕으로 "이렇게 이해했다"를 짧게 요약한다.
3. 위 6개 질문 세트 중 아직 답이 안 된 항목만 골라서 되묻는다.
4. 팀원의 답을 받기 전까지는 코드/설계 산출물을 다시 내놓지 않는다.

**STOP의 용도**:
- 세션 시작 전 예방용: "STOP, 이거 시작하기 전에 확인부터"
- 세션 중 개입용: 이미 코드를 짜기 시작했는데 뭔가 안 맞다 싶을 때, "STOP" 한마디로 즉시 멈추고 재확인 모드로 전환
- 자동 감지 조건이 애매하거나 트리거를 놓쳤다고 판단될 때의 안전장치

**주의**: STOP은 "취소"가 아니라 "재확인 모드 전환"이다. 작업 자체를 그만두는 게 아니라, drill-me 체크리스트로 되돌아가는 명령이다. 완전히 그만두고 싶으면 그렇게 별도로 말한다.
