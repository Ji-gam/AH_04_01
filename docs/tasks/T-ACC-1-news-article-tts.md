### 1. 배경 — 이건 새 기능이 아니라 미뤄둔 요구사항이다

T-LLM-6에서 건강정보 화면을 뉴스피드로 바꿀 때, 상세화면에 **[음성으로듣기]** 버튼을 만들어두고
비활성 상태로 두었다(`frontend/src/pages/InfoDetailPage/InfoDetailPage.tsx:126`). 이번에 그걸 켠다.

요구사항은 이미 문서에 있다. TRD T-ACC-1의 성공요건:

1. 마크다운/특수문자가 음성으로 그대로 읽히지 않는다(**전처리 필요**)
2. 재생 중 **정지 버튼으로 즉시 중단** 가능하다
3. **재생 상태 표시**

그리고 PRD F-ACC-1에 한 줄이 더 있는데, 이게 기술 선택을 좌우한다:

> 재생 중인 카드는 시각적으로도 구분되어 **어디를 읽고 있는지** 알 수 있다.

즉 "지금 이 단락을 읽고 있어요"를 화면에 표시해야 한다. PRD는 이 기능을
**고령 사용자 접근성**을 위한 것으로 명시하고 있다 — 그래서 기본 재생 속도, 버튼 크기, 상태 문구를
그 기준으로 잡는다.

> **범위 주의**: PRD는 "모든 주요 콘텐츠 카드"에서 음성 지원을 말하지만, 이번 작업은
> **뉴스 기사 상세화면 원문**만 대상으로 한다(2026-07-31, 박지은). 챗봇 답변 낭독(TRD `:204`)은

### 2. 기술 선택 — 왜 "브라우저 내장 음성"인가

두 갈래를 비교했다.

| | **브라우저 내장 음성** (채택) | 서버에서 mp3 생성 (기각) |
|---|---|---|
| 원리 | 기기에 이미 있는 음성 기능(`speechSynthesis`)에 텍스트를 넘긴다 | OpenAI TTS로 mp3를 만들어 저장·서빙한다 |
| 백엔드/DB | 변경 없음 | 컬럼 추가 + 마이그레이션 |
| 저장소 | 없음 | **이 레포에 S3가 없다.** 기존 파일 저장 패턴은 로컬 볼륨 하나(`document_storage`)뿐 |
| 리더 의존 | 없음 | `docker-compose.yml` 볼륨 추가 + EC2 반영 = **리더만 가능** |
| 비용 | 0 | 기사당 3~5센트 수준, 하루 30건이면 월 $30 내외 |
| 저장 용량 | 0 | 기사당 1.5~2MB → 월 약 1.8GB, 보관 정책 필요 |
| 클릭 후 첫 소리 | 즉시 | 생성에 20~40초 → 수집 배치에서 미리 만들어야 함 |
| **단락 하이라이트** | **쉽다** (아래) | **어렵다** (아래) |
| 음질 | 기기마다 다름 | 모든 기기 동일 |
| 잠금화면·이어폰 제어 | 불가 | 가능 |

**결정(2026-07-31, 박지은): 브라우저 내장 음성.** 서버 mp3는 손이 너무 많이 간다.

하이라이트 요구사항이 결정을 굳혔다. 브라우저 내장 음성은 **단락을 하나씩 순서대로 읽히고
"한 단락 끝났다"는 신호를 받을 수 있다** — 하이라이트가 공짜로 따라온다. 반면 서버 mp3는
3분짜리 소리 파일 하나일 뿐이고 그 안에 "지금 3번째 단락"이라는 정보가 없다. OpenAI TTS는
단어별 시간표를 주지 않으므로, 하이라이트를 하려면 단락마다 mp3를 따로 만들거나(파일 수 5~8배)
재생 시간으로 눈대중해야 한다.

수집된 기사 본문은 평균 **2,250자**, 최대 3,374자다(로컬 DB 실측, 7건). 소리로 3~4분짜리다.

### 3. 전처리는 저장하지 않는다 (런타임 처리)

읽기용 텍스트를 DB에 따로 저장하지 않고, **재생을 누른 순간 브라우저에서 변환**한다.
서버 왕복도 없다.

이유:
1. **공짜다.** 2,250자 문자열 치환은 1,000분의 1초도 안 걸린다. 저장해서 아낄 게 없다.
2. **저장하면 규칙을 못 고친다.** 이 규칙은 실제로 들어보며 계속 손볼 부분이다. 저장해두면
   규칙 하나 바꿀 때마다 컬럼 추가 → 마이그레이션 → 전체 재생성 배치 → 관리자 버튼이 딸려온다.
   런타임 처리면 코드를 고쳐 배포하는 것만으로 옛 기사까지 새 규칙으로 읽힌다.
3. **저장이 맞는 경우는 이미 기각했다.** 서버 mp3 방식이면 어차피 서버에서 한 번만 처리하니
   저장이 자연스러웠다. 그 방식을 안 하기로 했으니 저장 이유도 같이 사라졌다.

**트레이드오프**: 저장본이 없으니 규칙에 버그가 있으면 모든 기사에 동시에 나타난다.
그래서 전처리 모듈에 단위 테스트를 붙인다(4절 표가 그대로 테스트 케이스가 된다).

**화면에 보이는 본문은 원문 그대로 둔다.** 소리로 나갈 때만 다듬는다. 눈으로는 학술지 영문명이
보이고 귀로는 안 들리는 셈인데, 읽어주기 용도로는 그게 맞다.

### 4. 무엇을 다듬는가 — 실제 수집 데이터 기준

로컬 DB의 수집 본문을 직접 열어 확인한 것들이다. 상상한 케이스가 아니다.

> 미국심리학회(APA)가 발행하는 국제학술지 《정신병리학 및 임상과학 저널(Journal of
> Psychopathology and Clinical Science)》에 최근 게재된 논문은…

| 실제로 나온 것 | 그냥 읽히면 | 처리 |
|---|---|---|
| `《…》` 겹화살괄호 | 기호를 읽거나 이상하게 끊긴다 | 괄호만 제거(안쪽 글자는 남긴다) |
| `(Journal of Psychopathology…)` | 한국어 음성이 영문을 어색하게/한 글자씩 읽는다 | **괄호 안이 로마자·숫자·공백뿐이면 괄호째 삭제** |
| `(AI)` `(APA)` `(BMJ)` | "에이피에이" 중복 낭독 | 위 규칙 하나로 같이 처리(앞의 한국어에 이미 뜻이 있다) |
| `mg` `kg` `%` `℃` | 영문자 그대로 읽는다 | 밀리그램·킬로그램·퍼센트·도 |
| `30~40대` | 물결을 못 읽고 뭉갠다 | "30에서 40대" |
| `·` 중간점 | 붙여 읽어 뭉개진다 | 쉼표로 바꿔 숨을 쉬게 한다 |
| `http://…` URL | 주소를 한 글자씩 읽는다 | 삭제 |

`\n\n`(단락 구분)은 다듬기 대상이 **아니라 쪼개는 기준**이다. 단락 하나 = 발화 하나로 큐에 넣어야
하이라이트가 "지금 3번째 단락"을 정확히 알 수 있다.

본문은 T-LLM-6 수집 단계에서 이미 HTML을 걷어낸 평문이라(`app/services/health_news_source.py`),
마크다운 기호 처리 부담은 크지 않다. 그래도 TRD 성공요건이므로 `**` `##` `[]()` 같은 흔한
마크다운 기호는 방어적으로 함께 제거한다.

### 5. 아이폰 특성 — 설계에 미리 반영해야 하는 것

사용자는 모바일로 접속한다. 개발은 맥북에서 하는데, 맥 사파리와 아이폰 사파리가 **이 API에서
갈린다**. 나중에 고칠 문제가 아니라 처음부터 구조에 넣어야 하는 것들이다.

1. **첫 발화는 클릭 핸들러 안에서 동기로 실행해야 한다.** 아이폰은 클릭 핸들러 안에서 뭔가를
   기다린 뒤(`await`) 말을 시키면 무시한다. 맥은 그냥 봐준다. → **맥에서 되는 코드가 아이폰에서
   무음일 수 있다.** 목소리 목록 로딩을 기다리지 않고 일단 말을 시킨다.
2. **긴 텍스트는 중간에 끊긴다.** 단락 단위 큐가 필수고, 단락이 너무 길면 문장 단위로 한 번 더 쪼갠다.
3. **목소리 재고가 다르다.** 맥엔 한국어 음성이 기본 설치돼 있지만, 아이폰은
   `설정 > 손쉬운 사용 > 낭독 콘텐츠 > 음성`에서 한국어를 내려받아야 할 수 있다.
4. **홈화면에 추가한 앱 모드(standalone)에서 무음 사례가 보고돼 있다.** 우리 `manifest.json`이
   `"display": "standalone"`이다. 맥 사파리엔 이 모드가 없어 재현이 불가능하다.
5. **화면을 잠그면 재생이 멈춘다.** 이어듣기는 제공하지 않는다(5절 "스코프 밖").

**3·4번 대비 — 실패해도 데모가 깨지지 않게 한다.** 음성이 없거나 시작에 실패하면 버튼을 죽이지 않고
"이 기기에서는 음성 재생이 어려워요" 안내로 격하한다. 아이폰이 안 되더라도 다른 기기에서는 정상
동작하고, 화면이 망가지지 않는다.

### 9. 구현하면서 계획과 달라진 것

계획에 없었지만 실제로 만들어보고 확인한 것들이다. 리뷰어가 "왜 이렇게 했지?"를 코드에서
다시 추적하지 않도록 남긴다.

**(1) 자동 스크롤을 추가했다.** 하이라이트만 칠하면 26단락짜리 기사에서 곧 화면 밖으로 밀려나
"어디를 읽고 있는지"를 볼 수 없다. 그래서 읽는 단락이 화면에서 벗어났을 때만 화면 안으로
끌어온다(이미 보이면 건드리지 않아 화면이 매번 튀지 않는다).

**(2) `behavior: "smooth"`를 쓰지 않는다.** 처음엔 부드럽게 스크롤하도록 넣었는데, 실제
브라우저에서 **smooth 스크롤이 아예 무시되는 것을 확인했다**(`instant`는 728px 이동, `smooth`는
0px). 기기 설정 "동작 줄이기"가 켜져 있어도 같은 일이 생길 수 있다. 접근성 기능에서 스크롤이
안 되는 건 기능이 없는 것과 같아서, 부드러움을 버리고 확실함을 택했다.

**(3) `bg-card`는 이 프로젝트에 없는 토큰이었다.** 플레이어 배경에 썼더니 아무 색도 안 먹어
투명해지고 뒤로 지나가는 본문이 겹쳐 보였다. 색은 `src/index.css`에만 정의하는 규칙
(FRONTEND_UI_GUIDE_v1.0.md 2번)이고 거기에 `--card`가 없다. `bg-background`로 바꿨다
(`bg-secondary`는 단락 하이라이트가 쓰고 있어 헷갈리지 않게 피했다).

**(4) 낭독 텍스트 규칙 4개는 실제 수집 기사를 돌려보고 나서 추가됐다.** 단위 테스트만으로는
안 보였던 것들이다. `[자주 묻는 질문]` 대괄호, `된다?⋯정신건강`처럼 문장부호 뒤에 붙는
말줄임표, `인가요?A.`처럼 문장부호에 글자가 붙은 FAQ 표기, `까지...다섯`의 마침표 세 개.

#### 확인한 동작 (로컬 브라우저, 크로미움 + 한국어 음성 "유나")

| 항목 | 결과 |
|---|---|
| 클릭 핸들러 안에서 동기 발화 | `speak()` 1회, 제목 조각, `lang=ko-KR`, `rate=0.9` |
| 목소리 목록이 비어 있어도 재생 | `getVoices()` 0개인 시점에도 시작, 이후 "유나"로 잡힘 |
| 조각 이어가기 + 하이라이트 | 제목 → 단락 0 → 1 → 2 → 3, 하이라이트/진행표시 동행 |
| 자동 스크롤 | 4/26 단락에서 스크롤 728px, 하이라이트가 화면 안 |
| 속도 변경 | "빠르게" → `rate=1.15`, 같은 조각부터 다시 시작 |
| 일시정지 | 즉시 무음, 위치·하이라이트 유지, **낡은 `onend`로 큐가 진행되지 않음** |
| 이어듣기 | 같은 조각 재생, 바꾼 속도 유지 |
| 정지 | 즉시 무음, 플레이어 사라짐, 하이라이트 해제, 버튼 원복 |
| 화면 이탈 | 목록으로 이동 시 낭독 중단 |

**아직 확인 못 한 것**: 실제 아이폰·안드로이드에서 *소리가 들리는지와 목소리가 자연스러운지*.
음질 판단은 사람이 해야 하고, 아이폰 standalone 무음 위험(5절 4번)은 맥에서 재현이 불가능하다.

### 10. 스코프 밖 (다음으로 미룸)

- **화면 잠금·백그라운드 이어듣기** — 브라우저 내장 음성으로는 불가. 필요하면 서버 mp3 방식으로
  전환해야 하고, 그때 2절 표의 비용·저장소·리더 협조가 전부 따라온다.
- **잠금화면/이어폰 재생 제어** — 같은 이유
- **챗봇 답변 낭독**(TRD `:204`) — 훅을 재사용해 별도 작업으로
- **카드뉴스 모달 낭독** — 원문 낭독이 먼저 검증된 뒤에
- **목소리 선택 UI** — 기기가 주는 한국어 음성 중 첫 번째를 쓴다. 기기마다 재고가 달라
  선택 UI를 만들면 기기별로 목록이 달라 보인다.
- **본문에 인용된 영문 장문** — 예: `‘Understanding or undermining? When artificial
  intelligence chatbots quietly reinforce psychiatric symptoms’라는 제목으로 게재됐다`.
  한국어 음성이 영어를 어색하게 읽는다. 지우면 "라는 제목으로 게재됐다"만 남아 주어가
  사라지므로, 어설프게 손대기보다 그대로 뒀다. 괄호 안 영문 병기는 지우지만(4절) 따옴표 안
  인용은 남긴다.
