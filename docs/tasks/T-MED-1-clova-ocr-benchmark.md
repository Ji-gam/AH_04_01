# 처방전 인식 기능 설계 — 클로바 OCR 도입 검토
### (벤치마킹 앱 스크린샷 분석 → T-MED-1 반영안)

> 이 문서는 `ocr_기능.zip`에 포함된 벤치마킹 앱의 화면 흐름(처방전 촬영 → 분석 → 복약 스케줄 생성)을 분석하고, T-MED-1 태스크 범위 안에서 **클로바 OCR(Naver CLOVA OCR)을 어떻게 불러와 쓸지**, 그리고 **어떤 기능을 추가하면 좋을지**를 정리한 설계안입니다. T-MED-1의 허용 경로/금지 경로를 그대로 준수하는 것을 전제로 작성했습니다.

## 1. 벤치마킹 앱 화면 흐름 분석

스크린샷 순서(타임스탬프 기준)를 그대로 재구성하면 아래와 같은 파이프라인입니다.

| 단계 | 화면 | 핵심 동작 |
|---|---|---|
| 1 | 촬영 가이드 프레임 | "처방전을 프레임 안에 맞춰주세요" 안내 + 카메라 촬영/갤러리 선택 + 촬영 팁(전체 노출, 밝기, 평평하게) |
| 2 | 촬영 결과 확인 | 촬영된 이미지 미리보기 + "처방전 분석 시작하기" / "다시 촬영하기" |
| 3 | 분석 중 (진행률) | "이미지 분석 중..." → 하위 단계 노출: 약 정보 추출 중 → 복약 시간표 생성 중 → 거의 다 됐어요 |
| 4 | 분석 완료 토스트 | "N개의 약을 찾았습니다" |
| 5 | **약 목록 확인/수정 화면** | 항목별 매칭률(%), 약 이름(원문 그대로), 1회 용량/복용 횟수/일·투여 기간, 용법 텍스트, 인식된 원문 텍스트(OCR raw) 노출. 매칭률 100%로 표시 |
| 6~8 | 저장 후 재분석 로딩 | "약 정보 저장 완료" → "처방전을 읽고 있습니다" → "약 성분을 확인하고 있습니다" (2차 분석: 상호작용/음식 주의사항 판단) |
| 9~10 | **골든타임 시간표** | 시간대별(07:30 / 12:30 / 19:00)로 약을 그룹핑, 각 그룹에 사유 설명(예: "아침 식후 복용이 위장관 자극을 줄이고 흡수를 도울 수 있음") + 팁 문구 + 참고 출처(식약처 복약지침, FDA 등). "같은 시간대 약 묶어서 알림" 토글 |
| 11 | 약 목록 탭 | 약별 상세 카드: 용량·횟수·기간, 효능 설명(1줄), "탭하여 용량·횟수 수정" |
| 12 | **조합(상호작용) 탭** | "확인이 필요한 조합" — 특정 약 2개 조합에 대한 주의 문구 + "의료진·약사 확인 권장" 배지 |
| 13 | **음식 주의사항 탭** | 알코올 등 음식/성분 주의사항, 위험도 배지("주의") |

### 눈에 띄는 구조적 특징
- 4개 탭 구조: **시간표 / 약 목록 / 조합 / 음식** — 하나의 분석 결과를 다각도로 보여줌
- 모든 화면 하단에 **면책 문구** 고정: "본 서비스는 정보 제공 도구이며, 의학적 진단·처방을 대체하지 않습니다" + 출처(식약처·심평원·NIH)
- 매칭률(%) 을 약마다 노출해 신뢰도를 사용자에게 알림 → **DoD의 "신뢰도가 낮거나 후보가 여럿이면 사용자 확인 없이 등록 금지"**와 직접 연결됨
- OCR 인식 원문 텍스트를 그대로 병기해 사용자가 대조 확인 가능하게 함 (투명성)
- 시간표 생성은 "약 정보 추출"과 분리된 **2단계 파이프라인**(1차: OCR+약 식별, 2차: 상호작용/음식/시간대 로직)

## 2. 클로바 OCR 어떤 기능을 불러와야 하는가

CLOVA OCR은 크게 **General(범용) OCR**과 **Document OCR(템플릿/도메인 특화)** 두 축을 제공합니다. 처방전은 병원마다 서식이 크게 달라 고정 템플릿이 어렵기 때문에, 아래처럼 나눠 쓰는 것을 권장합니다.

### 2-1. 반드시 불러와야 하는 API 기능

| 기능 | 설명 | 이 태스크에서의 용도 |
|---|---|---|
| **General OCR (`/general`)** | 이미지 내 모든 텍스트 영역을 감지하고 텍스트/좌표(bounding box)/신뢰도(confidence)를 반환 | 처방전 사진 → 약품명, 용량, 용법, 투여기간 등 원문 텍스트 추출의 기본 엔진 |
| **필드별 confidence score** | General OCR 응답의 `fields[].inferConfidence` | 화면 #5처럼 약마다 매칭률(%)을 노출하는 근거. confidence가 낮으면 "후보 여러 개" 취급 |
| **Document 회전/기울기 보정 (`enableRotate`)** | 기울어지거나 회전된 이미지 자동 보정 옵션 | 촬영 팁("평평하게 펴주세요")에도 사용자가 삐뚫게 찍는 경우 대응 |
| **Table/Key-Value 구조 인식** (문서형 OCR 지원 시) | 표 형태로 된 처방전(약품명·용량·횟수·기간이 표로 정리된 한국 처방전 특성)의 행/열 구조 인식 | 스크린샷 #2에서 보듯 처방전은 표 형태 → 단순 텍스트 나열보다 표 파싱이 정확도에 크게 기여 |

> 참고: 실제 API 스펙(엔드포인트명, 요청 포맷, 응답 필드명)은 네이버 클라우드 플랫폼 콘솔에서 발급받은 도메인별 계약에 따라 달라지므로, 개발 착수 전 **CLOVA OCR 공식 문서에서 최신 스펙 확인 필요** (자율 판단 범위 내 — OCR 라이브러리 내부 파라미터 튜닝은 에이전트 자율 결정 가능하다고 되어 있으나, 외부 API 계약 자체는 확인이 필요).

### 2-2. 파이프라인 상 호출 순서 (제안)

```
[1] 이미지 업로드 (프론트 → 백엔드 presigned url 또는 multipart)
        │
[2] ai_worker/tasks/medication_task.py
        │  ├─ CLOVA OCR General 호출 → raw text + bbox + confidence
        │  ├─ (선택) 전처리: 명암/기울기 보정 후 재호출
        │
[3] ai_worker/schemas/medication_schema.py
        │  └─ OCR raw 결과 → 약품 후보 파싱 (정규식/룰 기반 or LLM 보정)
        │     - 약품명, 1회 용량, 복용 횟수/일, 투여기간, 용법 텍스트 추출
        │     - confidence 낮은 필드는 candidates[] 로 유지 (자동 확정 금지)
        │
[4] app/services/medication_service.py
        │  └─ 후보 리스트 + confidence → DB 매칭 (의약품 마스터 데이터, 예: 식약처 공공데이터)
        │     - 매칭률 계산, 동일 약품 여러 개 매칭 시 후보 노출
        │
[5] 사용자 최종 확인/수정 (프론트 — 화면 #5, #11 형태)
        │
[6] 확정 후 스케줄 생성 로직 (시간대 그룹핑, 조합/음식 주의사항 매핑)
```

## 3. 추가하면 좋은 기능 (벤치마킹에서 얻은 인사이트 기반)

T-MED-1의 완료 정의(DoD)와 자율 판단 허용 범위 안에서 **바로 반영 가능한 기능**과, F-MED-2(상호작용 경고) 등 **타 태스크와 조율이 필요한 기능**을 구분했습니다.

### 3-1. T-MED-1 범위 내에서 바로 구현 가능

- **OCR confidence → 매칭률(%) UI 노출**
  후보가 여러 개거나 confidence가 임계값 미만이면 자동 등록을 막고 사용자 선택 UI로 전환 (DoD 1번 요건과 정확히 일치)
- **OCR 원문 텍스트 병기**
  파싱된 약품 정보 옆에 OCR이 인식한 원문 텍스트를 같이 보여줘, 사용자가 오인식을 즉시 확인·수정 가능하게 함 (`인식된 텍스트: ...` 형태, 화면 #5 참고)
- **분석 진행 단계 세분화 & 진행률 UI**
  "이미지 업로드 중 → 텍스트 인식 중 → 약품 매칭 중 → 스케줄 생성 중" 각 단계별 상태를 API가 반환하도록 하여, 프론트가 프로그레스바/단계 텍스트를 보여줄 수 있게 함 (사용자 체감 대기시간 완화, P95 3초 요건과 별개로 UX 향상)
- **식별 실패 시 수동 검색 전환 플로우**
  OCR 신뢰도가 임계값 이하이거나 매칭 실패 시, 자동으로 "약품명 직접 검색" 화면으로 전환하는 fallback (DoD 2번 요건과 일치). 검색은 약품 마스터 DB 대상 자동완성으로 구현
- **용법 텍스트 → 시간 슬롯 추천 (초기값)**
  "1일 2회 식후" 같은 용법 텍스트를 파싱해 추천 복용 시간(아침 7:30, 저녁 19:00 등)을 초기값으로 제안하고, 사용자는 시간만 조정 (DoD 3번 요건: "시간 선택 외 추가 입력 없이 완료"). 초기값 로직은 자율 판단 범위 내 (매칭률 임계값처럼 내부 파라미터)
- **동일 시간대 약 그룹핑 알림**
  여러 약이 같은 시간대에 몰릴 경우 하나의 알림으로 묶어 발송하는 옵션 (스크린샷 #9 "같은 시간대 약 묶어서 알림" 토글) — 알림 발송 자체는 알림 인프라(공유 자원) 영향이 있는지 확인 필요

### 3-2. 공유 계약 변경 또는 타 도메인 조율이 필요 (완료 보고에 기재 권장)

- **약물 상호작용(조합) 경고 탭** — 벤치마킹 화면 #12의 "확인이 필요한 조합" 기능은 PRD 상 **F-MED-2(상충 경고)** 영역과 명시적으로 겹칩니다. T-MED-1의 "반드시 멈춰야 하는 경우" 조건("매칭률 계산 로직이 다른 도메인의 데이터 구조 변경을 요구하는 경우")에 해당할 수 있으므로, **이 기능은 이번 태스크에서 구현하지 않고 F-MED-2와의 인터페이스(약 리스트 → 상호작용 체크 요청)만 열어두는 것을 권장**합니다.
- **음식 주의사항 탭** — 마찬가지로 약물-음식 상호작용 데이터가 필요하며, F-MED-2 또는 별도 참조 데이터 도메인과 연계될 가능성이 높습니다. 완료 보고서에 "공유 계약 변경 필요 사항"으로 기재하고 이번 스프린트 범위에서는 제외를 제안합니다.
- **의약품 마스터 데이터 소스** — 벤치마킹 앱은 식약처·심평원·NIH 공공데이터를 출처로 명시합니다. 매칭에 사용할 마스터 데이터가 `app/models/medication_model.py` (고정 계약)에 이미 존재하는지, 아니면 별도로 시딩이 필요한지 확인이 선행되어야 합니다 — 이는 금지 경로(app/models)를 건드리는 문제이므로 "공유 파일 변경 필요"로 보고할 사안입니다.

### 3-3. 신뢰성/안전 관련 — 놓치기 쉬운 디테일

- **면책 문구 고정 노출**: 모든 분석 결과 화면 하단에 "의학적 진단·처방을 대체하지 않습니다" 문구를 고정 배치 — 법적/신뢰성 리스크 완화 차원에서 프론트 구현 시 누락 없이 반영 권장 (frontend/src/pages/medication/** 허용 경로 내에서 처리 가능)
- **재촬영/다시 분석 경로**: 매 단계마다 "다시 촬영하기" 옵션을 열어둬 OCR 오인식 시 사용자가 쉽게 재시도할 수 있게 함
- **분석 완료 후에도 수정 가능**: "약 정보 수정하기" 버튼을 최종 확정 이후에도 유지 — 등록 후 오류 정정 경로 확보
