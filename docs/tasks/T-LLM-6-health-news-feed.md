### 1. 배경 — 왜 "새로 만들기"가 아니라 "대체"인가

지금 사용자가 홈 화면의 **[건강정보]** 바로가기(`/info`, `frontend/src/pages/HomePage/HomePage.tsx:43`)로
들어가서 보는 화면은 T-LLM-3 구현물이다. 이게 뭐냐면,
**LLM이 매일 건강 팁을 지어내서 보여주는 것**이다. 실제 기사가 아니라 AI가 쓴 글이다.

그래서 두 가지가 계속 아쉬웠다.

1. **출처가 없다.** AI가 지어낸 글이라 "어디서 나온 얘기냐"에 답할 수가 없다. 건강 정보인데 근거가 없다.
2. **이미지가 없다.** 넣을 그림이 애초에 없어서, 지금은 카테고리별 고정 플레이스홀더로 때우고 있다
   (`frontend/src/lib/contentCategoryDisplay.tsx`).

(참고: 하단 텍스트 탭은 이전 개편에서 없어졌고, 지금 정보 화면의 유일한 입구는 홈 화면 바로가기다.
`frontend/src/components/common/Layout.tsx:12` 참고.)

T-LLM-6은 이 자리를 **실제 언론사 기사**로 바꾼다. 기사에는 원문 링크와 사진이 딸려 오므로 위 두 문제가
동시에 풀린다. 그리고 긴 원문을 읽기 싫은 사용자를 위해 **카드뉴스 요약**을 제공한다.

**결정(2026-07-30, 박지은)**: T-LLM-3은 T-LLM-6으로 **대체**한다. 건강정보 화면은 앞으로 뉴스 피드 하나만
보여주고, 기존 LLM 생성 팁카드 기능(테이블·서비스·관리자 화면)은 제거한다. 두 기능을 공존시키지 않는다 —
같은 자리를 두 벌의 코드가 차지하면 지저분해지기 때문.

#### 대체 대응표

| 기존 (T-LLM-3) | 새로 (T-LLM-6) |
|---|---|
| `health_contents` 테이블 (질환×카테고리×날짜당 1건) | `health_news` 테이블 (기사 URL 단위) |
| 관리자 **[콘텐츠 생성]** 버튼 → LLM이 팁 생성 | 관리자 **[뉴스 수집]** 버튼 → RSS 수집 ← *수동 트리거 자리* |

| 대시보드 "카테고리별 콘텐츠 수" | 대시보드 "소스별 수집 기사 수" |

### 3. 확정된 설계 결정

#### 3-1. 카드뉴스 품질은 "코드가 보장"한다

카드가 예쁜 이유를 LLM에게 맡기지 않는다. 역할을 이렇게 자른다.

- **LLM이 정하는 것**: 글자와 숫자뿐 — `tag` / `stat` / `substat` / `text`, 그리고 `icon_key`
- **코드가 정하는 것**: 배경 그라데이션, 아이콘 배치, 워터마크, 여백, 글자 크기 — 전부

이렇게 하면 LLM이 최악의 답을 줘도 **카드가 못생겨질 수는 없다.** 글의 내용이 심심할 수는 있어도
레이아웃이 깨지지는 않는다. 여기에 방어를 두 겹 더 둔다: 스키마의 `max_length`(글자수 제한),
그리고 CSS `line-clamp`(그래도 길면 잘라냄). 프로토타입 만들 때 실제로 글자가 넘쳐 아이콘을 밀어낸
사고가 있었기 때문에 둘 다 필요하다.

#### 3-2. 아이콘은 "객관식"으로 받는다

LLM에게 "어울리는 아이콘을 알려줘"라고 자유롭게 물으면, 우리가 가지고 있지도 않은 아이콘 이름을
말한다. 그래서 **미리 정한 목록 안에서만 고르게** 한다. Pydantic의 `Literal`로 선택지를 못 박으면
LLM은 그 중 하나만 답할 수 있고, 답이 곧 프론트 아이콘 맵(`frontend/src/lib/cardNewsIcons.ts`)의
키가 된다 — 해석하는 중간 단계가 필요 없다. (그래서 "아이콘을 구조화할 두 번째 LLM"은 필요하지 않다.)
그 맵은 `Record<CardIconKey, LucideIcon>` 타입이라, 백엔드에 아이콘이 추가됐는데 프론트에서
빠뜨리면 `npm run typecheck`가 잡아준다.

아이콘 라이브러리는 **lucide**를 쓴다. 프론트엔드에 `lucide-react`가 이미 깔려 있어서 새 의존성도,
새 라이선스 검토도 없다. (Font Awesome을 추가하는 안은, 앱 전체가 이미 lucide 모양으로 통일돼 있어
시각적으로 튀고 의존성만 늘어서 접었다.)

**확정(2026-07-30)**: 아이콘 **52종**. 검증 방법은 계획보다 나은 길이 있었다 — 외부(unpkg)에 물어보는
대신 **프론트에 이미 설치된 `lucide-react@1.27.0` 패키지의 아이콘 파일 목록(2,007종)과 직접 대조**했다.
그게 실제로 렌더될 아이콘의 유일한 진짜 기준이다. 52종 전부 존재 확인, 중복 0건.
파일명이 kebab-case라 `icon_key` 값이 그대로 아이콘 파일 이름과 같다.

목록은 `app/dtos/health_news_dto.py`의 `IconKey`가 유일한 원본이고, 런타임에서 쓰는 `ICON_KEYS`
튜플은 `get_args()`로 거기서 뽑는다 — 두 곳을 따로 관리하면 반드시 어긋나기 때문.
프로토타입에서 쓴 11종(`moon` `dumbbell` `footprints` `timer` `droplet` `scroll-text` `heart`
`clipboard-list` `shield-check` `gauge` `flask-conical`)은 모두 포함돼 있다.

LLM이 목록에 없는 이름을 답하면 검증 예외를 던지는 대신 중립 아이콘(`info`)으로 바꾼다 —
카드 하나를 못 그리는 것보다 낫다.

#### 3-3. 스키마 일반화는 검증 완료

당뇨 기사로 만든 스키마를 **완전히 다른 기사**(2026 ACC/AHA 이상지질혈증 가이드라인 개정)에 그대로
적용해봤다. 아이콘 5종이 겹치지 않게 선택됐고, 목록에 아이콘을 하나도 추가하지 않았으며, 레이아웃
수정도 없었다. → 질환이 달라도 같은 틀이 버틴다. (`card-news-heart.html`)

#### 3-4. 뉴스 소스: 코메디닷컴 하나로 시작

RSS 후보를 실제로 찔러봤고, 제대로 된 `application/rss+xml`을 준 곳은 **`kormedi.com/feed`** 하나였다
(헬스조선 `rss.xml`/`feed` → 응답 없음, 하이닥 → 404, 연합뉴스 health.xml → 200이지만 실은 HTML,
연합뉴스TV → 영상 위주).

코메디는 WordPress 기반이라 `content:encoded`에 **본문 HTML 전체 + `<img>` + `<figcaption>`**이
들어 있다. 즉 **별도 스크래핑 없이 본문과 사진을 한 번에 받는다.** 이게 코메디를 1번 소스로 고른
가장 큰 이유다.

> 저작권: 이 서비스는 아카데미 제출용 PoC이며, 저작권은 이 기능에서 고려하지 않기로 사용자가
> 명시적으로 결정했다(2026-07-30). 대신 원문 링크와 출처명은 항상 함께 표시한다.

**코메디 피드는 건강기사만 주지 않는다 — 걸러내야 한다** (2026-07-30 실측):
실제로 10건을 받아보니 4건이 건강정보가 아니었다.

| RSS 카테고리 | 예시 제목 | 처리 |
|---|---|---|
| `AI 공시뉴스` | "일동제약, 2분기 당기순이익 흑자전환…" | **버림** (상장사 공시, 투자자용) |
| `바이오·제약` | "올릭스 비만약 후보, 원숭이 내장지방 29.2% 줄여" | **버림** (제약사 파이프라인) |
| `기획ㆍ연재-셀럽헬스` | "홍현희, 살 뺄 때 지켰다는 '3가지 습관'" | **유지** (다이어트/식단 팁이 담김) |
| `건강` `의료` `음식` 등 | "혈압 낮추려면 3가지 붉은 음료 즐겨라" | 유지 |

**결정**: 위 두 카테고리는 **수집 단계에서 버려 DB에 넣지 않는다**(2026-07-30, 박지은). 저장 후
화면에서 숨기는 방식이 아니다 — 쓸데없는 행이 안 쌓이고 카드요약 LLM 호출도 낭비되지 않는다.
단, 몇 건을 버렸는지는 수집 결과에 숫자로 보고한다(조용히 버리면 파싱 실패와 구분이 안 된다).
`source_categories` 컬럼을 저장하기로 한 판단이 여기서 바로 값을 했다.

| 질문 | 결정 | 이유 |
|---|---|---|
| 개인화(지병 맞춤 정렬) | **2단계로 미룸** | 파이프라인이 실제로 도는지부터 확인. 스키마에 `disease_code` 자리만 미리 비워둔다 |

### 4. 데이터 스키마

```python
# app/models/health_news.py
class HealthNews(Base):
    __tablename__ = "health_news"
    __table_args__ = (
        # 같은 기사를 다시 수집해도 중복으로 쌓이지 않게 하는 유일한 열쇠.
        UniqueConstraint("source", "source_url", name="uq_health_news_source_url"),
    )
    id: Mapped[int]  # BigInteger, PK
    source: Mapped[str]  # String(50)  "KORMEDI" 등 출처 코드
    source_name: Mapped[str]  # String(100) 화면에 보일 출처명 "코메디닷컴"
    source_url: Mapped[str]  # String(500) 원문 링크
    title: Mapped[str]  # String(300)
    published_at: Mapped[datetime]  # 기사 발행일 — 피드 정렬 기준 (index)
    body_text: Mapped[str]  # Text, 본문 평문(단락 구분 "\n\n")
    image_url: Mapped[str | None]  # String(500) 대표 이미지, 없을 수 있음
    image_caption: Mapped[str | None]  # String(500) 사진 설명(<figcaption>)
    disease_code: Mapped[str | None]  # String(50)  2단계에서 채움. 1단계는 NULL
    source_categories: Mapped[list | None]  # JSON, RSS <category> 목록 — 2단계 태깅 힌트
    card_summary: Mapped[dict | None]  # JSON, 카드뉴스 슬라이드 배열
    fetched_at: Mapped[datetime]  # 수집 시각
```

#### 구현 중 바꾼 설계 3건 (2026-07-30, 실제 피드를 파싱해보고 결정)

1. **`body_html` → `body_text` (평문 저장)**. 원래는 `content:encoded`의 HTML을 그대로 저장할
   계획이었다. 그런데 그러면 프론트에서 `dangerouslySetInnerHTML`로 그려야 하고, 그건 **외부
   사이트가 우리 앱에 스크립트를 심을 수 있는 통로**가 된다. 수집 시점에 평문으로 뽑아두면
   프론트는 단락을 `<p>`로만 그리므로 그 통로가 아예 생기지 않는다.
   대가로 본문의 굵은 글씨와 중간 링크를 버리는데, 뉴스 읽기에는 손실이 크지 않다고 봤다.
2. **`image_caption` 추가**. 코메디 `<figcaption>`에 "사진=게티이미지뱅크" 같은 **출처 표기**가
   들어있다. 사진만 가져오고 이 표기를 버리면 안 된다.
3. **`source_categories` 추가**. RSS `<category>`에 `["건강","아토피","알레르기",...]`처럼
   질환명이 들어온다. 2단계 질환 태깅의 가장 좋은 힌트인데, **지금 안 받으면 되돌릴 수 없다** —
   피드에서 밀려난 기사는 다시 받을 방법이 없기 때문. 지금은 화면에 쓰지 않는다.

**왜 기존 `health_contents`를 재활용하지 않는가** (검토 결과, 2026-07-30):

- `(disease_code, category, content_date)` **복합 유니크 제약**이 "하루에 한 건"만 허용한다. 코메디는
  같은 날 여러 건이 올라오므로 정면으로 충돌한다.
- `disease_code`가 **NOT NULL**이다. 방금 수집한 기사는 아직 질환 분류를 안 했으므로 채울 값이 없다.
- `image_prompt`는 "AI가 그림을 그릴 때 쓸 지시문"용 칸이다. 우리가 가진 건 완성된 이미지 URL이라,
  이름과 의도가 다른 칸에 억지로 넣는 셈이 된다.

즉 두 테이블은 정체성이 다르다 — 하나는 "매일 새로 짓는 글", 하나는 "URL로 식별되는 실제 기사".
그래서 새 테이블을 만들고, 기존 테이블은 5단계에서 지운다.

**`card_summary`를 별도 테이블로 빼지 않은 이유**: 기사 1건에 카드요약도 1개(1:1)라서 조인할 이유가
없다. 나중에 "요약 여러 버전"이 필요해지면 그때 분리한다.

**카드요약 JSON 모양** (`app/dtos/` 의 Pydantic 스키마가 이 형태를 강제한다):

```jsonc
{
```

### 7단계: 소스 확장 (2026-07-31)

#### 후보 25개를 실제로 찔러본 결과

"API로 불러올 수 있고 이미지도 있는 것"을 찾았는데, **한국 언론사는 거의 전부 같은 CMS를 쓴다**는
것이 이번 조사의 핵심 발견이다. RSS 규격도 기사 페이지 구조도 똑같아서 **파서 하나로 여러 매체를
처리할 수 있다.** 다만 그 CMS의 RSS는 본문을 주지 않는다.

| | 코메디닷컴 | CMS 계열 매체 (9곳 확인) |
|---|---|---|
| RSS가 주는 본문 | **1,781자 (전문)** | **299자 (요약)** |
| RSS가 주는 이미지 | 있음 | **없음** |
| RSS `<category>` | 81종 | **없음** |
| 기사 페이지 | 읽을 필요 없음 | `itemprop="articleBody"`에 본문·사진·캡션 전부 있음 |

**결정(2026-07-31, 박지은): 기사 페이지를 한 번 더 읽는다.** 299자 요약만으로는 카드 3~5장을 만들
재료가 부족하고, [음성으로 듣기]가 299자만 읽고 끝난다. 비용은 기사 1건당 HTTP 1회이고 수집
배치에서만 발생한다(사용자 요청 경로와 무관). robots.txt는 두 매체 모두 `/admin/`만 금지한다.

#### 채택한 매체

| 매체 | 피드 | 본문 길이(실측) | 왜 |
|---|---|---|---|
| 코메디닷컴 | `kormedi.com/feed/` | 1,493~3,453자 | 기존. 유일하게 RSS에 전문이 온다 |
| **헬스경향** | `k-health.com/rss/S1N10.xml` | 1,053~1,984자 | **"건강정보" 섹션**. 최신 10건이 전부 일반인 건강정보였다 |
| **코리아헬스로그** | `koreahealthlog.com/rss/S1N1.xml` | 842~2,334자 | "News" 섹션. 질환 설명형 기사가 많다 |

**섹션 피드가 곧 필터다.** CMS 계열은 `<category>`를 주지 않아 코메디처럼 카테고리로 걸러낼 수 없다.
대신 전체기사(`allArticle.xml`) 대신 섹션 피드를 고르면 같은 효과가 난다 — 헬스경향 전체기사는
병원 홍보·의료정책이 절반인데 "건강정보" 섹션은 깨끗했다.

**매체당 5건 상한**(`MAX_ARTICLES_PER_SOURCE`). 카드요약 LLM 비용이 기사 수에 정비례하므로 상한이
곧 비용 상한이다. 상한을 넘긴 기사는 버리는 게 아니라 미루고, 그 수를 `over_limit`로 보고한다.

#### 7단계에서 실제로 밟은 함정 4개

1. **`pubDate`가 RSS 표준이 아니었다 — 이 매체 기사가 전부 버려지고 있었다.** CMS 계열은
   `2026-07-31 17:15:31`처럼 **타임존 없는 한국 시각**을 준다. `parsedate_to_datetime`이 실패해서
   조용히 건너뛰었고, 수집 결과가 "코메디 10건"으로만 나왔다(오류도 안 났다). 더 나쁜 건 그냥
   파싱만 고치면 안 된다는 점 — 한국 시각을 그대로 저장하면 UTC로 저장되는 코메디 기사보다
   9시간 미래가 되어 피드 맨 위를 이 매체가 늘 차지한다. `_parse_published_at`이 두 형식을
   모두 받아 UTC로 맞춘다.
2. **본문 앵커를 `id="article-view-content-div"`로 잡으면 안 된다.** 그 문자열이 페이지 상단
   자바스크립트(복사할 때 출처를 붙이는 코드)에 **먼저** 등장해서 본문을 놓친다. schema.org 표준
   `itemprop="articleBody"`를 앵커로 쓴다.
3. **본문 끝을 구조(`<div id="tem-type-N">`)로 자르면 본문이 잘린다.** 헬스경향은 그 id를 본문
   중간 블록에도 쓴다. 처음엔 1,053자 기사가 452자로 잘렸다. 대신 "가장 먼저 나오는 종료 표시"
   에서 자른다 — `>FAQ<`, `</article>`, 저작권자, 무단전재.
4. **기사 끝에 AI가 생성한 FAQ 문답이 붙는다**(헬스경향). 기사 내용을 되풀이하는 Q&A라서
   남겨두면 카드요약이 같은 말을 재료로 쓰고 [음성으로 듣기]가 같은 이야기를 두 번 읽는다.

그밖에 실측으로 처리한 것: 이미지가 `/news/photo/...` 상대경로로 오는 매체가 있어 절대 URL로
바꾼다(그대로 두면 우리 도메인 기준으로 해석돼 사진이 깨진다), 제목 앞에 BOM을 붙여 보내는
매체가 있어 떼어낸다, 브라우저 UA로 위장하지 않아도 두 매체 모두 정상 응답한다.

##### 6단계에서 실제로 밟은 함정 3개

1. **`box-sizing: content-box`로 카드 폭이 어긋났다.** 카드 폭을 315px로 지정했는데 실제로는
   355px로 그려져 오른쪽 peek이 사라졌다. 원인은 이 프로젝트가 **Tailwind Preflight를 꺼놔서**
   전역 `border-box` 리셋이 없다는 것 — 좌우 패딩 20px씩이 폭에 더해진 것이었다
   (315 + 40 = 355). 전역으로 되돌리면 아직 마이그레이션 안 된 화면들이 깨지므로
   `.cardnews-card`에만 국소로 `box-sizing: border-box`를 줬다.
2. **퍼센트 flex-basis를 믿지 못했다.** 처음엔 CSS만으로 풀려고 `flex: 0 0 100%` + 덱
   `padding-inline: 30px`을 썼는데(이론상 "화면폭 - 60"), 스크롤 컨테이너 + `aspect-ratio`
   조합에서 기대값이 나오지 않았다. ResizeObserver로 덱 폭을 직접 재서 CSS 변수에 넣는 방식으로
   바꿨다 — 계산식이 코드에 드러나서 검증도 쉽다.
3. **템플릿 리터럴 안 주석에 백틱을 써서 화면이 백지가 됐다.** 주입하는 `<style>`이 템플릿
   리터럴인데 CSS 주석 안에 \`box-sizing: border-box\`처럼 백틱을 쓰자 문자열이 끊겼다.
   HMR은 "Failed to reload"만 남기고 화면은 백지가 되어 원인이 안 보였고, `npm run typecheck`가
   정확한 줄을 짚어줬다.

##### 검증하지 못한 것

관리자 화면(`/admin`)은 로그인 계정이 필요해 브라우저로 직접 눌러보지 못했다. 대응 API는
테스트 17개로 덮여 있고 화면 코드는 typecheck/build를 통과했지만, **버튼을 실제로 눌러본
확인은 아니다** — 시연 전에 한 번 눌러봐야 한다.

> **5·6단계 경계를 조정했다.** 원래 표에는 "관리자 대시보드 통계 교체"가 5단계에 있었는데,
> 프론트 수정이 5단계와 6단계에 쪼개져 들어가면 PR이 지저분해진다. 그래서 **5단계는 백엔드만**,
> **6단계에서 프론트 전부(사용자 화면 + 관리자 UI) + 구코드 제거**로 옮겼다.
> 대시보드 통계는 백엔드에 `news_count_by_source`를 새로 추가해뒀고(기존
> `content_count_by_category`는 6단계에서 함께 제거), 화면 반영은 6단계에서 한다.

##### 5단계 API 모양

| 메서드 | 경로 | 용도 |
|---|---|---|
| GET | `/api/v1/news` | 피드(발행일 최신순). 비로그인 가능. **본문 미포함** |
| GET | `/api/v1/news/{id}` | 상세. 본문 + `card_summary` + `disclaimer` 동봉 |
| POST | `/api/v1/admin/news/collect` | **[뉴스 수집] 트리거** (수집 + 카드요약). 감사로그 기록 |
| GET | `/api/v1/admin/news` | 수집 목록(`source_categories` 노출 → 필터 기준 조정 근거) |
| PATCH | `/api/v1/admin/news/{id}` | 제목/본문 수정 |
| DELETE | `/api/v1/admin/news/{id}` | 왜곡·부적절 기사 내리기 |

피드 응답에 본문을 담지 않는 이유: 기사마다 1~3KB씩이라 목록만 무거워진다. 상세에서 받는다.
상세 응답에 카드요약을 함께 싣는 이유: [카드요약보기]에 추가 요청이 없어야 한다(TRD "별도 대기 없이").
`has_card_summary`가 false인 기사도 피드에 보여준다 — 원문은 이미 읽을 수 있으므로 감출 이유가 없고
버튼만 비활성으로 두면 된다.

##### 4단계에서 실측으로 고친 것 (모두 실제 LLM 응답에서 발견)

| 발견 | 조치 |
|---|---|
| `stat`이 빈 문자열 `""`로 옴(31장 중 3장) → 가장 큰 글씨 자리가 빈칸으로 그려짐 | `stat`을 `str \| None`으로 바꾸고 공백은 `None`으로 정규화. **템플릿이 stat 없는 카드를 "글자 카드"로 그려야 한다(6단계 할 일)** |
| 규칙을 필드 설명으로 옮기니 `stat` 생략이 3/31 → 10/29로 급증 | 프롬프트 규칙을 "① 기사 숫자 → ② 짧은 핵심 표현 → ③ 그래도 안 되면 비움" 순서로 명시. 재측정 결과 1/30(3%) |
| **부호 뒤집힘**: 원문 "몸무게가 63kg까지 **빠졌다**" → LLM이 `+63kg`(늘어난 것처럼) | 프롬프트에 방향 확인 규칙 추가("헷갈리면 부호를 빼고 값만"). 재생성 결과 `63kg`으로 교정 |
| **설명문이 2줄밖에 안 나옴**(2026-07-31 실측): `TEXT_MAX=60`에 프롬프트가 "한 문장"이라 지시. LLM은 제한에도 못 미치는 33~45자를 씀. 카드 폭 315px·폰트 14px에서 한 줄이 약 20자라 2줄. 정작 카드에는 **292px(약 15줄)가 비어 있었다** | `TEXT_MAX` 60 → **110**, 프롬프트에 "**3~5줄(70~110자)을 채우세요**"를 `stat` 규칙과 같은 방식(명시적 지시)으로 추가. 길이를 늘리는 방법을 "기사에 있는 내용을 덧붙이는 것"으로 못 박아 지어내기를 막았다 |

##### 카드요약 다시 만들기 (2026-07-31 추가)

위처럼 프롬프트나 글자 수 제한을 손질하면 **이미 요약이 있는 기사는 옛 기준으로 남는다** —
수집 배치는 요약이 비어 있는 기사만 고르기 때문이다(`list_missing_card_summary`). 그래서
관리자 화면에 **[카드요약 다시 만들기]** 를 추가했다(`POST /admin/news/card-summaries/regenerate`,
스크립트는 `--regenerate-summaries`).

**기존 요약을 먼저 지우지 않는다.** 새로 만들기를 시도하고 성공한 것만 덮어쓴다 — 먼저 비우면
LLM이 중간에 실패했을 때 쓸 만했던 요약까지 잃는다. 테스트로 고정해뒀다.

**남은 위험(설계로 못 막는 것)**: 위 부호 오류처럼 **LLM 요약이 기사를 왜곡할 수 있다.** 프롬프트로
줄일 수는 있지만 없앨 수는 없다.

**결정(2026-07-30, 박지은)**: "관리자 승인 후 노출" 게이트는 **두지 않는다**. 대신 두 가지로 대응한다.

1. 카드뉴스에 **"AI가 요약했습니다 · 원문 보기"** 표기와 면책 문구를 항상 함께 둔다(REQ-INFO-004).
   사용자가 원문으로 바로 갈 수 있으면 요약이 틀렸을 때 확인할 길이 있다.
2. 관리자가 기사·요약을 **삭제**할 수 있게 한다(5단계) — 사후 대응.

승인 게이트를 뺀 이유: 노출 여부 컬럼 + 관리자 심사 UI + 피드 필터가 추가로 필요하고, 무엇보다
시연 전에 매번 사람이 수동으로 순재해야 한다. 이 서비스는 아카데미 제출용 PoC라 그 비용이
얻는 것보다 크다.

**관찰**: 셀럽헬스 기사(연예인 가십)가 카드 품질이 가장 낮다 — 기사에 인용할 숫자가 적어
`stat`이 "혼자", "2위"처럼 어색해진다. 유지하기로 결정했으나(3-4절), 6단계에서 화면으로 보고
다시 판단할 여지가 있다.

`dev` 기준 최신 마이그레이션은 `0058_add_diet_kcal_reasons.py`이므로 새 리비전은 `0059`(생성),
`0060`(DROP)이다.

> **주의(실제로 밟은 함정)**: 리비전 번호는 반드시 **`dev` 최신을 받은 뒤에** 확인해야 한다.
> 다른 브랜치에서 번호를 세면 그 사이 dev에 들어온 마이그레이션이 안 보여서 번호가 충돌한다
> (`Revision 0054 is present more than once`). 새 리비전을 추가한 뒤에는 `uv run alembic heads`로
> **head가 하나인지** 확인한다 — 두 개면 브랜치가 갈라진 것이다.

### 6. 영향도와 리더 협조 시점

지금 EC2에 SSH로 직접 붙을 수 있는 사람은 리더뿐이므로, "언제 리더가 필요한가"를 미리 못 박아둔다.

| 단계 | 인프라 영향 | 리더 협조 |
|---|---|---|
| 2 (스키마) | 마이그레이션 1건. 배포 시 `alembic upgrade`만 돌면 됨 — **평소 배포와 동일** | 불필요 |
| 3 (수집) | 로컬 실행. EC2에서 외부 HTTP(코메디) 아웃바운드가 필요하지만 이미 OpenAI를 호출하고 있어 열려 있음 | 불필요 |
| 4 (카드요약) | 기존 `ai_worker` 경로 재사용. **LLM 호출량이 기사 수만큼 늘어남** → 비용 증가는 사전 공유 | 공유만 |
| 5~6 (API·프론트·제거) | 마이그레이션 1건(DROP). **되돌리기 어려운 작업** — 머지 전 팀 공지 | 공지 |
| 7 (소스 확장) | 없음 | 불필요 |
| **8 (Celery)** | **`docker-compose.yml`에 worker/beat 서비스 신규 추가** | **승인 + 배포 협조 필수** |

**가장 먼저 알려야 할 것**: 지금 `docker-compose.yml`에는 **Celery worker도 beat도 없다**
(서비스는 redis / mysql / fastapi / ai-worker / nginx뿐). 그래서 "주기 자동 수집"은 코드만으로 안 되고
컨테이너 추가가 필요하다. `docker-compose.yml`은 팀 소유권 모델상 **리더 소유 파일**이므로
사전 승인 대상이다.

**협조 요청 시점 — 결정(2026-07-30, 박지은)**: 리더에게는 **8단계에 실제로 도달했을 때** 요청한다.
소스 확장(7단계)까지 못 갈 수도 있어서 미리 알리면 김칫국이 되기 때문. 대신 요청이 급해지지 않도록
8단계 착수 전에 `docker-compose.yml` 변경안(추가할 서비스 정의)을 미리 작성해 함께 전달한다 —
리더가 검토만 하면 되게.
