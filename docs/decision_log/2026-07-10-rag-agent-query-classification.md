# 2026-07-10 — 질환 논문 검색 에이전트: "확률적 판단"을 "결정론적 라우팅"으로 개선한 과정

> 발표/평가 자료용 기록. T-LLM-7(I단계) → T-LLM-7-1(III단계, Query Rewriting) →
> T-LLM-7-2(라우터 분리 + 강제 도구 호출)까지, 문제 발견부터 근본 원인 분석,
> 리서치 기반 재설계, 실측 검증까지의 전체 과정을 남긴다.

## 요약

`ai_worker`의 질환 논문 검색 에이전트가 "당뇨병"처럼 표준 표기와 다른 변형 표현이나,
"지방간 진행 여부를 검사 없이도 알 수 있어?"처럼 부정문으로 된 질문에서 **일관성 없이**
도구 호출을 거부하는 문제가 있었다. 단순히 프롬프트 문구를 계속 다듬는 방식(1차 시도)은
"확률적 개선"에 그쳤고, **문제의 구조적 원인**(하나의 LLM 판단이 "질환 인식"과 "호출
여부 결정"을 동시에 떠맡고 있었던 것)을 찾아 **역할을 분리**하고 나서야 완전히
해결됐다.

## 문제 발견: T-LLM-8 미니 평가셋

10개 질문으로 실제 API를 호출해 육안 비교하는 평가셋(`ai_worker/scripts/eval_paper_agent.py`)을
LangSmith 트레이싱과 함께 도입한 결과, 다음 케이스가 예상과 다르게 "논문 검색 범위
밖"으로 거부됨을 발견했다:

| 질문 | 기대 동작 | 실제 동작 |
|---|---|---|
| "뇌졸중 치료는 빠를수록 좋다는 게 사실이야?" | 뇌혈관질환 논문 검색 | 거부 |
| "지방간 진행 여부를 검사 없이도 알 수 있어?" | 간질환 논문 검색 | 거부 |

당시 구조(T-LLM-7)는 `langchain`의 `create_agent`(LangGraph 기반)가 도구 1개를
쥐고, 시스템 프롬프트 하나로 "이게 논문 요청인지"와 "질환명이 뭔지"를 동시에
판단하게 되어 있었다.

## 1차 시도: Query Rewriting (T-LLM-7-1) — 부분 개선에 그침

도구 호출 전에 질문을 정규화하는 별도 LLM 호출(`rewrite_disease_query`)을 추가했다.
"5개 질환 중 하나로 골라라"가 아니라 "표준 명칭이 뭐야?"를 열어두는 방식으로 설계해,
나중에 질환이 늘어나도(ADHD, 비만 등) 프롬프트를 안 건드려도 되게 했다(질환 목록은
`SUPPORTED_DISEASES`에서 동적 interpolation).

**결과**: "뇌졸중" 케이스는 해결됐지만, "지방간"과 새로 추가한 "심장마비" 케이스는
여전히 실패했다. 원인은 이 시점엔 파악하지 못한 채 "메인 에이전트가 힌트를 받고도
스스로 다시 판단해버린다"는 정도로만 기록하고, 완전 해결이 아니라는 점을 정직하게
남겼다(PR #62).

## 근본 원인 분석: 왜 "확률적"이었나

메인 에이전트의 시스템 프롬프트를 rewrite 힌트를 신뢰하도록 고치지 않았다는 게
1차 원인이었지만, 더 깊이 보면 **"질환 인식"과 "이게 논문을 요청하는 질문인가"는
서로 다른 축의 판단**인데 하나의 LLM 호출(또는 하나의 시스템 프롬프트)이 이 둘을
동시에 처리하고 있었다는 게 진짜 원인이었다.

## 웹 리서치로 확인한 해법

Agentic RAG 아키텍처 사례를 조사한 결과, 이 문제에 정확히 대응하는 두 가지 표준
패턴을 확인했다:

1. **Router 컴포넌트 분리** — "이 질문이 검색이 필요한지, 잡담인지"를 판단하는
   Router를 도구 실행과 분리해서 둔다.
   [Agentic RAG Series - Query Routing](https://sajalsharma.com/posts/comprehensive-agentic-rag/),
   [LangGraph 공식 문서](https://docs.langchain.com/oss/python/langgraph/agentic-rag)
2. **강제 도구 호출(Forced tool calling)** — 결정론적 파이프라인에는 모델이 매번
   자유 재량으로 도구를 고르게 두는 것보다, 조건이 충족되면 개발자가 도구 호출을
   강제하는 편이 안정적이다.
   [Reliable Tool Calling — ChangeGamer](https://changegamer.ai/resources/reliable-tool-calling)

## 재설계 (T-LLM-7-2)

판단을 **구조화 출력 2개 필드**로 명시적으로 분리했다:

```python
class QueryClassification(BaseModel):
    disease: str | None  # 언급된 질환의 표준 명칭 (관용구는 null)
    is_information_request: bool  # 정보/확인을 원하는 질문인지
```

두 조건이 **모두 참**일 때만 코드가 `search_disease_paper`를 직접 호출한다(LLM이
다시 "부를지 말지" 재판단하지 않음). 이 과정에서 `create_agent`(LangGraph) 기반의
"에이전트가 스스로 도구를 고르는" 루프 자체가 불필요해져, "분류 → (결정론적 검색) →
답변 생성"이라는 더 단순한 파이프라인으로 재구성됐다.

### 뜻밖의 발견: 한국어 관용구 오탐 위험

재설계 도중 "이 질환명 힌트를 신뢰해서 강제로 도구를 부르면, 신체 장기를 빗댄
한국어 관용구(예: '나 심장이 너무 쫄려...', '간이 콩알만해지다')에서 엉뚱한 논문을
들이밀 위험이 있지 않나?"라는 질문이 나왔다. 실제로 테스트해보니 **정확히 그 문제가
재현**됐다:

```
'나 심장이 너무 쫄려...' -> '심장질환'   # 오탐
'시험 때문에 심장 떨려 죽겠어' -> '심장질환'  # 오탐
```

`disease`만 보고 강제 호출했다면 이 문제를 그대로 안고 갔을 것이다. `is_information_request`
축을 분리해둔 덕분에, 이런 케이스는 "질환 단어는 감지되지만 정보 요청은 아님"으로
정확히 걸러졌다:

```
'나 심장이 너무 쫄려...' -> disease='심장질환', is_information_request=False → 검색 안 함
```

## 최종 검증 (실제 API 키, 16문항)

| 케이스 유형 | 예시 | 결과 |
|---|---|---|
| 표준 표기 질문 | "당뇨 논문 알려줘" | ✅ 검색 성공, 수치 인용 |
| 변형 표현 | "뇌졸중 치료는...", "지방간 진행 여부는..." | ✅ 검색 성공 (기존 실패 케이스 전부 해결) |
| 미지원 질환 | "ADHD 관련 논문 있어?" | ✅ 정중한 안내 (도구 미호출, 오답 아님) |
| 무관 질문 | "오늘 날씨 어때" | ✅ 정상 거부 |
| **한국어 관용구** | "나 심장이 너무 쫄려...", "간이 콩알만해지는 일이 많아" | ✅ 오탐 없이 정상 거부, 오히려 공감형 응답 |

## 핵심 교훈 (발표 포인트)

1. **"확률적으로 좋아진 것 같다"는 프롬프트 튜닝의 한계 신호다** — 증상 완화가 아니라
   근본 원인(하나의 판단 축에 여러 책임이 섞여 있음)을 찾아 구조를 분리해야 결정론적으로
   해결된다.
2. **판단 축을 분리하면 검증도 쉬워진다** — "질환 인식 실패"와 "의도 파악 실패"를
   섞어서 보면 원인 파악이 안 되지만, 분리하면 각각을 독립적으로 테스트/디버깅할 수
   있다.
3. **성능 개선 하나를 적용하면 새로운 리스크가 따라온다** — 강제 호출로 재설계하는 순간
   "관용구 오탐" 위험이 새로 생겼고, 이를 사전에 의심하고 직접 실험으로 검증한 뒤에야
   안전하게 배포할 수 있었다.
4. **평가셋(육안 검증)이 없었다면 이 문제 자체를 몰랐을 것이다** — 자동화된 pytest는
   "회귀 방지"만 할 뿐, 애초에 무엇이 잘못됐는지는 실제 LLM 호출을 사람이 관찰해야
   드러난다.
