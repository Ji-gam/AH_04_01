## 에러 처리 규칙(CODING_RULES.md 9번)의 배경

실제로 겪은 사고: 프론트에서 회원가입 실패 메시지가 `[object Object]`로만 찍힌 적이 있다. 원인은 FastAPI의 유효성 검증 실패(422) 응답이 `{"detail": "..."}`(문자열)가 아니라 `{"detail": [{"loc": [...], "msg": "..."}, ...]}`(배열)로 오는데, 그걸 그대로 `Error`에 넘겨서 배열이 문자열로 강제 변환된 것이었다. 이 사고를 계기로 `detail` 타입을 먼저 분기하는 공통 파싱 규칙을 `CODING_RULES.md` 9번에 신설했다.

## 문서 버전 관리 방식의 배경

`CLAUDE.md`의 "문서 버전 관리" 규칙("파일명은 버전 때문에 다시 바꾸지 않는다")은 `remedi_mweb_co` 시절부터 있던 정책이다. 한 번은 파일명에 버전 접미사(`_v1.0`, `_v1.1`)를 넣는 방식을 썼다가, 그 파일을 참조하는 다른 모든 문서를 버전 올릴 때마다 같이 고쳐야 해서 유지보수 비용이 너무 컸다 — 그래서 "살아있는 문서"는 파일명을 영구 고정하고 헤더 버전만 올리는 방식으로 폐기·전환했다. `PRD`/`TRD`/`api_spec` 같은 "원본 스냅샷 문서"만 예외로 파일명 버전 접미사를 유지하는 이유는, 이 문서들은 팀이 자주 고치지 않고 "그 시점 버전 그대로"를 추적하는 목적이 크기 때문이다(2026-07-07, `docs/plan`/`docs/dev`로 재이동).

## RAG 개발 기간 동안의 화면별 대응 전략 (Tier 구조)

| Tier | 대상 | RAG 필요 여부 | 처리 방식 |
| --- | --- | --- | --- |
| Tier 0 | 홈 위젯, 순응도 히트맵 | 없음 | RAG 완성 대기 없이 즉시 개발 |
| Tier 1 | 건강 콘텐츠 생성 파이프라인 | 생성만 필요 | 배치 생성 → 캐시 테이블 저장 → 화면은 캐시만 읽음 |
| Tier 2 | 약품 안전 정보 안내, 인식 데이터 기반 맞춤 가이드 | 사용자별 실시간 판단 필요 | RAG 완성 전까지는 Service가 규칙기반 stub 리턴 (`docs/dev/sample_code_recog/` 실제 코드 참고) |
| 실시간 필수 | AI 챗봇 상담 | 있음 | RAG 파이프라인 완성 시점에 맞춰 통합 |
