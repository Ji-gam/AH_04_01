# 제안: 질환 논문 검색에 실제 외부 API 연동 (PubMed / Semantic Scholar)

> 상태: **논의 중 — 아직 승인 안 됨**
> 관련 로드맵: "ai_worker · RAG 원정기 v2" IV단계("진짜 검색으로 갈아타기")
> 관련 규칙: `AGENTS.md` 8번 "Task Contract에 없는 새 외부 API/서비스 연동은 반드시 멈추고 물어야 함"

## 배경

`ai_worker`의 질환 논문 검색 기능(T-LLM-7~7-2)은 지금까지 5대 질환(암/심장질환/뇌혈관질환/
당뇨/간질환) 각각 논문 1편씩을 로컬 JSON 스텁으로 저장해두고 검색하는 방식으로 만들어져
있다. 목적은 "실제 검색 API 없이도 에이전트/판단 로직을 검증"하는 것이었고, 이 목적은
T-LLM-7-2까지 충분히 달성했다(질환 인식, 관용구 오탐 방지, 결정론적 라우팅 전부 실제
API 키로 검증 완료).

로드맵은 다음 단계로 "가짜 논문 1개 대신 실제 검색 결과 여러 개 받아보기"를 제시하며,
이를 명시적으로 **"승인 필요" / "팀 승인 구간"**으로 표시해두었다. 지금까지 `ai_worker`는
(LLM 호출 자체는 외부 API이지만) 검색 자체는 완전히 로컬/오프라인이었는데, 이번 변경은
**검색이 처음으로 외부 네트워크에 의존**하게 되는 전환점이라 팀 논의가 필요하다고 판단했다.

## 무엇을 도입하려는가

`ai_worker/tools/paper_search.py`의 `search_disease_paper()` 내부 구현만 교체한다
(함수 시그니처·도구 인터페이스는 그대로 유지):

- **PubMed E-utilities** (NCBI 제공) — 논문 검색 표준, API 키 없이도 사용 가능(단 요청 빈도 낮음)
- **Semantic Scholar API** — 초록 요약, 인용 정보 등 부가 메타데이터 제공, 무료 티어 존재

둘 중 하나 또는 병행 사용을 검토 중이며, 최종 선택은 이 논의 이후 결정한다.

## 좋은 점

- **진짜 후보가 여러 개 생김** — 지금은 질환당 논문 1편뿐이라 "여러 후보 중 고르기"(V단계:
  임계값 튜닝, Re-ranking 등)를 연습할 재료 자체가 없다. 실제 API가 붙어야 그다음 로드맵
  전체(V~VI단계)가 의미를 갖는다.
- **최신성** — 스텁 데이터는 고정된 가짜 수치라 시간이 지나도 안 바뀌지만, 실제 논문
  검색은 최신 연구를 반영한다.
- **커버리지 확장** — 5대 질환에 한정되지 않고, 사용자가 실제로 어떤 질환을 묻든 검색
  시도가 가능해진다(단, 판단 로직상 "지원 여부"와는 별개 문제).
- **아키텍처 변경 최소화** — T-LLM-7-2에서 "분류 → 검색 → 생성" 파이프라인으로 이미
  정리해둔 덕분에, 이번 교체는 `search_disease_paper()` 내부만 바꾸면 되고 분류기/
  결정론적 라우팅 로직은 전혀 안 건드려도 된다.

## 고민해야 할 점 (단점/리스크)

| 영역 | 내용 |
|---|---|
| **비용/쿼터** | PubMed는 무료지만 요청 빈도 제한이 있고(초당 요청 수 제한, API 키로 완화 가능), Semantic Scholar도 키 없이는 낮은 rate limit. 트래픽이 늘면 제한에 걸릴 수 있음 |
| **지연시간** | 로컬 스텁은 즉시 응답이지만, 외부 API는 네트워크 왕복 시간이 추가됨. 챗봇 실시간 스트리밍 요구사항(F-LLM-2, API P95 3초 기준)에 영향을 줄 수 있어 실측 필요 |
| **테스트/CI 안정성** | 지금 `ai_worker/tests`는 전부 로컬 mock이라 결정론적인데, 실제 API가 붙으면 외부 서비스의 장애/스키마 변경에 테스트가 흔들릴 위험. 회귀 테스트는 계속 mock 유지 + 실제 연동 확인은 별도 수동/통합 테스트로 분리 필요 |
| **데이터 라이선스/ToS** | 논문 초록을 가져와 그대로 인용/재가공하는 것에 대해 각 API의 이용약관을 확인해야 함 |
| **장애 시 폴백 정책** | 외부 API가 응답하지 않을 때 사용자에게 어떻게 안내할지(기존 스텁으로 폴백? 명확한 에러?) 설계 필요 — `AIWorkerUnavailableError` 계약과 일관되게 갈지 결정 필요 |
| **응답 형식 통합** | PubMed와 Semantic Scholar는 응답 스키마가 다름 — 어느 하나만 쓸지, 병행해서 정규화된 내부 포맷으로 합칠지 결정 필요(후자는 하이브리드 검색(VI단계)과도 맞닿음) |

## 팀에서 결정해주었으면 하는 것

1. PubMed / Semantic Scholar 중 무엇으로 시작할지 (또는 병행)
2. API 키 발급/과금 주체 및 관리 방식(`envs/.local.env` 개인 키 vs 팀 공용 키)
3. 지연시간 실측 후 스트리밍 요구사항에 문제가 되면 어떻게 할지(캐싱을 앞당길지 등 — 로드맵 VIII단계 "캐싱"과 순서 재조정 여지)
4. 장애 시 폴백 정책
